# 性能基准 (Performance Benchmark)

测试环境：Windows 11 笔记本（本地 SQLite WAL）、Uvicorn 单进程、Locust 20 并发虚拟用户、30 秒采样。
工具：`locustfile.py`（只读负载：列表 6 : 看板 3 : 到期 2 : 掌握度 1 : 语义搜索 1 : 完整备份 1 : 健康检查 1）。

## 基准结果（2026-10-07，v2.20，282 请求，0 失败）

数据口径：demo 账号名下 18 道错题（经 `GET /api/questions` X-Total-Count 实读）；
与 2026-09-19 时点相比题量与构成有差异（九批开发期间含导入/冒烟数据），趋势对比仅供参考，
绝对值以本表为准。语义搜索预热一次后采样（嵌入模型冷启动不入表，见对比段）。

| GET /api/stats/dashboard | 48 | 32ms | **12ms** | 180ms | 204ms | 1.7 |

### 与 2026-09-19 基线对比

1. **热路径 P50 仍为个位数至低双位数毫秒**：列表 10ms（持平）、到期 8ms（略优）、看板 12ms（持平）、
   掌握度 12ms（新入表）——SQL 下推 + WAL 的结论在九批交付后依然成立，无热路径回归。
2. **语义搜索 P95 从 3.2s 降到 390ms**：两点差异导致——①本次采样前预热了一次语义查询
   （嵌入模型冷启动不入表，09-19 基线把冷启动算进了采样）；②数据构成不同。
   热路径 P50 270ms → 220ms 大致持平，「本地嵌入为主要耗时」的结论不变。
3. **export_full 为 zip 生成重操作，非典型读**（首基线，单独标注）：18 题量级下
   中位 18ms / P95 340ms；耗时随题目与图片数量线性增长，个人量级（数百题）下
   预计仍在亚秒到秒级，不适用 req/s 横向对比。
4. **零失败**：282 请求 0 错误、0 5xx（与 09-19 一致，WAL + busy timeout 持续有效）。
5. 聚合 P95 2200ms 由 on_start 的 bcrypt 登录拖高（每虚拟用户启动各一次），
   真实读路径 P95 见分端点表；登录 2.3s 是刻意的安全开销（结论不变）。

机器负载口径：Windows 11 笔记本（与 09-19 同机），应用版本 v2.20.0（本批同提交升至 v2.20.1，无代码差异），
Locust 2.46.0 headless，20 VU / 30s / 每秒 5 ramping。

## 关键结论

1. **核心读接口 P50 ≈ 10ms**：SQL 下推（标签/关键词过滤在数据库完成）+ WAL 模式后，列表与看板在 20 并发下保持个位数至低双位数毫秒。
2. **语义搜索是重尾**（P50 270ms / P95 3.2s）：首查含嵌入模型冷启动；热路径约 250-400ms，主要耗时在本地嵌入计算。生产部署建议接入远程嵌入 API（`EMBEDDING_BASE_URL`）。
3. **登录 2.3s 是设计使然**：bcrypt（12 rounds）+ 失败延迟 1s 是刻意的安全开销，非性能问题。
4. **零失败**：30 秒 20 并发下无错误、无 5xx、无锁等待超时（WAL + busy timeout 生效）。

## 已做的性能工作

- 列表/到期/计数全部 SQL 下推（避免 Python 侧全量过滤）
- SQLite WAL + busy timeout 30s（多线程写安全）
- 图片上传自动压缩（≤1600px JPEG）
- AI 解析异步任务化（不占请求线程）

## 检索评测（Recall@K / MRR / NDCG）

工具：`python -m scripts.eval_retrieval`。方法：以每道错题的标签为查询，检验目标题是否出现在 top-K（18 条查询，2026-09-19）。JSON 报告输出至 `data/eval_report.json`（含 Recall@1/3/5/10、MRR、NDCG@10、延迟 P50，供管线回归对比）。

| 指标 | 关键词 | 向量 | RRF 融合 |
|---|---|---|---|
| Recall@1 | 44% | 11% | 33% |
| Recall@5 | 72% | 33% | 67% |
| Recall@10 | 94% | 61% | 78% |
| MRR | 0.578 | 0.218 | 0.477 |
| NDCG@10 | 0.660 | 0.308 | 0.550 |
| 延迟 P50 | ~0ms | 177ms | ~0ms |

**诚实结论**：在本数据集（查询=精确标签、且大量错题共享同一标签，如 8 题同属「一元二次方程」）上，关键词单路已接近上限，RRF 融合反而被弱向量路稀释。

**何时融合有价值**：查询是自然语言（同义词/错别字/跨题描述）而非精确标签时——关键词 LIKE 命中不了，向量路提供独有召回，融合才有增益。因此实现保留为**双路融合可配置**，评测脚本可持续跟踪。

改进方向：本地 ONNX 嵌入对短中文标签区分度低 → 接入远程 bge-m3 嵌入（已支持）或加 rerank 精排（已留钩子）后重测。

## 检索金标集持续门禁（2026-10-04 起）

路线 #4 落地：12 条金标语料（专属用户隔离 + 每条双问法）进 pytest，随 CI 每次提交回归
（`tests/test_retrieval_quality.py`）：

| 门禁 | 阈值 | 2026-10-04 实测 |
|---|---|---|
| 关键词路 Recall@1（独有词，确定性） | = 100% | **12/12** |
| 混合路 Recall@3（学生自然语句，真实向量检索） | ≥ 60% | **67%（8/12）** |
| 关键词查询走混合路不丢目标（阈值语义边界） | = 100% | **12/12** |

语义未进 top3 的 4 例（判别式/三边关系/正弦定理/掷骰子概率）均为中文意译问法，
与既有结论一致：内置 MiniLM 对中文 paraphrase 区分度弱。门禁取 60% 兜住
「语义路被打穿」级别的回归；接入 BGE-M3 后应上调并更新本表。

**管线修复（Batch 01）**：重排此前只看到关键词命中的文档；现已修正为「Dense/Keyword 各取 Top-50 → RRF → 一次性 Hydrate 全候选 → 重排 → 阈值过滤 → 分页」，重排器可见完整候选集，且有 15+ 个管线测试守护该顺序。
