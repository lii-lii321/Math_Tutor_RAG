## 一、项目速览

MathMaster Edu 是一个面向中学数学刷题/复习场景的全栈个人项目：Streamlit 前端（`frontend/pages/` 共 10 个页面模块，`nav.py` 注册 9 项导航）以服务层为主要复用面，FastAPI 作为面向外部多端的第二入口，后端按 services → repositories → models 分层；核心能力包括关键词+向量双路混合检索（RRF 融合 + 可选重排 + 多级降级）、多提供商 AI 抽象与 13 工具 Tool-use Agent、SymPy 确定性验证闸门（三态聚合）、SM-2 间隔重复调度与时间加权掌握度引擎。外部依赖（AI 提供商、限流器、任务队列、向量库）统一采用「Protocol + 双后端 + 失败回退」模式，主流程不被可选组件阻断。质量侧由 358 个测试用例的四层测试体系与含 lint 门禁的 4-job CI 支撑；同时诚实保留三处已量化的短板：实测覆盖率 79% 低于文档声称的 ~90% 且无门禁、文档/指标数字随开发漂移（测试数 287→335→340→353→358、提交数 144→147、迁移数 11/12）、reaper 与 Redis 限流 except 回退分支零测试。

### 2.1 分层架构与配置/数据可移植性（deep）

**能力说明**

services → repositories → models 的后端分层，前端经服务层复用业务逻辑，FastAPI 网关与 Streamlit 前端同源复用服务层；会话模型为 session-per-operation，这是针对 Streamlit 执行模型做的显式取舍而非默认选择。配置侧一条链贯穿应用、Alembic、测试三个入口：SQLite 零配置起步、`DATABASE_URL` 一键切 PG/MySQL；12 版 Alembic 迁移链带空库冒烟测试与一次 PG16 实机验证记录。

**仓库证据**

- **分层边界（2026-10-01 复核修正后的准确表述）**：`frontend/pages/` 共 10 个页面模块（`frontend/nav.py:23-33` 的 PAGES 注册表为 9 项导航）；全仓 `findstr /s /n "repositories" frontend\*.py` **零命中**——前端没有任何对 `backend.repositories` 的引用，也无自建 HTTP 客户端，仓储层仅被 `backend/services/{auth,data_health,question_mixins}.py` 引用（材料 import 扫描）。需要如实记录的越层引用：`pages/assistant.py:11` import `backend.config`、`pages/auth.py:6-7` import `backend.database` 与 `backend.models.schemas`、`pages/settings.py:9-10` 同——「前端只 import backend.services」不成立，分层纪律的真实边界是「零仓储依赖、无 HTTP 客户端」。
- 路由层只做校验与状态码转换（`api/routers/questions.py:93-133`）；服务层按领域拆 8 个 Mixin 且公共 API 零改动（`backend/services/question_service.py:26-36`）。
- session-per-operation 的取舍写在注释里（`question_service.py:6-7`：Streamlit 脚本重跑+多线程模型下长事务会泄漏连接并撞 SQLite 写锁），配套决策文档 `docs/ARCHITECTURE.md` §1–§2。
- 配置链三入口：`backend/config.py:24-126`（pydantic-settings 的 Field ge/le、Literal、field_validator 启动期校验）；alembic `env.py` 的 URL 优先级链（`-x url=` > `DATABASE_URL` > settings）与 `render_as_batch` 兼容 SQLite；测试 `tests/conftest.py:12-20` 用环境变量指向临时库。`lru_cache` 配置进程单例并带默认密钥告警，「只告警不拒启」是注释写明的有意取舍（`config.py:129-139`、`database.py:121-126`）。
- 迁移链：解析全部 down_revision 为无分叉线性链 5167fa289d4f→fd4aa70dcf97→8ac7bf6a7a43→161851d2f63f→b98b7ec07b27→7d967aaa71b5→b09bda59c235→74fbffade73a→55c91901b5d9→7f0da979939c→c463cd3fa41c（材料记录 11 节点；实测指标为 12 版，存在漂移）；迁移冒烟测试空库 upgrade head 并断言版本表（`tests/test_migrations.py:7-24`）；CHANGELOG 2.10.0 记录 287 用例在 PG16 实机验证通过。
- 提交记录：材料记录 144 次 conventional commits；2026-10-01 复核 `git rev-list --count HEAD` = 147（多出的 3 个为 2.12.0 批次）。

**面试怎么讲（含可能的追问与答法）**

核心叙事：「我的分层不是口号而是可机械验证的——import 检索证明前端零仓储依赖、无自建 HTTP 客户端，仓储不被服务层以外引用；session-per-operation 是针对 Streamlit 执行模型做的取舍，这个决策写在代码注释和 ARCHITECTURE.md 里。我也如实记录越层的部分：前端有 3 处直连 config/database/schemas，这是收口对象，不是隐藏项。」

可能的追问与答法：

- **问：「frontend→api 这个说法字面成立吗？」** 答：不成立，我会主动澄清——Streamlit 前端直连服务层，FastAPI 是供外部多端的第二入口，复用靠共享代码而非统一 HTTP 契约；契约统一是我诚实记录的遗留议题，不是已完成的事。
- **问：「说前端『零业务逻辑』，证据呢？」** 答：可机械验证的部分是零仓储依赖与无 HTTP 客户端（全仓检索 repositories 零命中）；但前端并非只 import services——assistant/auth/settings 三个页面直连 config/database/schemas，这类越层引用我会主动列出来，而不是宣称完美分层。
- **问：「为什么 session-per-operation 而不是长事务？」** 答：Streamlit 每次交互重跑脚本且多线程执行，长事务会泄漏连接并撞 SQLite 写锁（`question_service.py:6-7` 注释原文），短事务是适配该执行模型的决策。
- **问：「切数据库真的零成本吗？」** 答：一条配置链贯穿应用/Alembic/测试三入口，SQLite 零配置起步、`DATABASE_URL` 一键切 PG；但我会诚实补充——CI 只跑 SQLite，PG 兼容是一次性人工批次验证（CHANGELOG 2.10.0 的 287 用例 PG16 实机记录），不是持续保障，MySQL 无实测记录。

**诚实短板**

- 「frontend→api」并非字面成立：前端直连服务层，FastAPI 是第二入口，契约统一未完成。
- 分层纪律有越层例外：`assistant.py:11`、`auth.py:6-7`、`settings.py:9-10` 直连 config/database/schemas，「只 import services」的旧表述不成立（2026-10-01 复核修正）。
- session_scope 未 100% 统一：`comment_service.py:42` 与 `job_service.py:44/75/93/116` 仍直接 `with SessionLocal()`，`api/deps.py:71-80` 重复实现 session_scope。
- `POST /api/questions/import` 收 `payload: dict` 绕过 Pydantic 校验（`api/routers/questions.py:152-161`）。
- CI 只跑 SQLite；PG 兼容是一次性人工批次验证而非持续保障，MySQL 无实测记录。
- 迁移文件基本由 autogenerate 产出（头部命令注释残留）缺手工调优；配置中心缺 fail-fast 模式与配置变更审计。

### 2.2 外部依赖全面降级设计（deep）

**能力说明**

所有外部依赖遵循「默认零依赖、可升级、坏了降级」：AI 提供商、限流器、任务队列、向量库均为 Protocol + 双后端 + 失败回退，主流程永不被可选组件阻断；绝大多数降级路径有专门测试守护（两处例外见诚实短板）。任务队列用「DB 状态机为唯一事实源 + 启动期 reaper + 取消双检」解决进程内线程队列崩溃后的僵尸任务问题。

**仓库证据**

- AI 工厂按配置选 openai_compatible/gemini/mock，ImportError 降级演示模式、无 Key 进 mock 并告警（`backend/services/ai/__init__.py:17-42`）。
- 限流器 memory/redis 可换：RateLimiter Protocol + InMemory/Redis（INCR+EXPIRE NX）双实现（`backend/utils/rate_limit.py:9-17,20-84`；进程内滑动窗口另见 `backend/utils/request_limiter.py:12-37,50-89`），Redis 依赖缺失/连接失败回退进程内并打 warning「保证限流始终可用」（`api/deps.py:30-53`）；rate_limit 是端点依赖工厂挂 4 个高成本端点（`deps.py:56-68`、`api/routers/agent.py:30`）。
- 向量库三处降级关键词（`backend/services/rag.py:82-85,130-132,220-222`：初始化/写入/检索）；RQ 不可用回退线程（`backend/jobs/queue.py:61-69`）。
- 任务队列容错：jobs 表为唯一状态源 pending→running→success/failed/cancelled（`job_service.py:7`）；启动期 `JobService.reap_stuck_jobs(timeout=30min)` 回收僵尸任务且失败不阻断启动（`api/main.py:88-96`、`job_service.py:110-135`）；取消双检——service 仅 pending 可取消（`job_service.py:73-89`）+ worker 取任务时二次校验（`backend/jobs/tasks.py:23-35`）；AI 重试独立于队列且策略集中一处（`ai/base.py:160-170`、`openai_compat.py:24` 的 max_retries=0）。
- 降级路径的测试：`tests/test_rag_degradation.py`、`test_redis_limiter.py`、`test_job_queue.py:99-180`（材料子集实跑 29 passed 内执行）、`test_hybrid_retrieval.py:103-119`（rerank 故障回退融合序）；限流后端选择路径由 `tests/test_redis_request_limiter.py:35-71` 的 TestBackendSwitch 覆盖（Redis 选中与默认进程内两条）。

**面试怎么讲（含可能的追问与答法）**

核心叙事：「所有外部依赖在我的系统里都是协议抽象 + 双后端 + 失败回退，绝大多数降级路径有专门测试——可选组件挂掉只降级、不阻断、不崩溃。可以现场讲 Redis 限流挂了为什么降级进程内而不是让请求失败。」

可能的追问与答法：

- **问：「Redis 挂了为什么降级进程内而不是直接报错？」** 答：限流是保护性组件，不该反过来成为可用性故障点——回退进程内计数并打 warning 留痕，「保证限流始终可用」（`api/deps.py:34` 注释原文）；但两后端窗口语义不一致（进程内滑窗 vs Redis 固定窗），故障切换瞬间配额会跳变，这是诚实记录的已知取舍，不是假装无缝切换。
- **问：「线程队列崩了留下僵尸任务怎么办？」** 答：jobs 表是唯一状态源，启动期 reaper 以 30 分钟超时回收遗留 running 任务且失败不阻断启动；取消语义靠 service 侧 pending 校验与 worker 侧二次校验双保险。
- **问：「『每条降级路径有测试』真的每条都有吗？」** 答：不，有两处例外我会主动交代——reaper 零测试覆盖、`deps.py:46-51` 的 Redis except 回退分支无用例（后端选择路径有，异常回退分支没有）；这两处已列入提升路线第 2 条。
- **问：「降级会不会掩盖真实失败？」** 答：不会装作无缝——每次降级打告警留痕；但我也承认 broad except 一刀切曾造成数学验证器静默失效（CHANGELOG v2.11），这是本块与 2.4 节共同面对的教训。

**诚实短板**

- reaper 无任何测试（2026-10-01 复核：`findstr /s /n "reap" tests\*.py` 零命中；全库仅 `api/main.py:94` 与 `job_service.py:110` 两处引用）。
- `api/deps.py:46-51` 的 Redis **except 回退分支**无用例覆盖——需精确表述：相邻的**后端选择路径**已被 `tests/test_redis_request_limiter.py:35-71`（TestBackendSwitch，Redis 选中与默认进程内两条）覆盖，未被覆盖的是「Redis 依赖缺失/连接失败」这条异常分支本身。
- 两后端窗口语义不一致，故障切换瞬间配额跳变；进程内 `_hits` 按 key 无淘汰，长尾常驻内存；固定窗口边界突发 2x。
- ThreadedJobQueue daemon 线程进程退出即丢任务；RQ 入队为裸 enqueue，无队列级 retry。
- 登录失败锁定+固定 1s 延迟（`auth.py:17-38`）有测试但防爆破整体维度较薄。
- 四组工厂的选择均为静态解析，需重启生效；无接口契约测试保证三个 AI 实现行为一致。

### 2.3 混合检索管线（deep）

**能力说明**

**面试怎么讲（含可能的追问与答法）**

### 2.4 AI 工程链路（deep）

**能力说明**

一条主线贯穿：既不信任 LLM 的输出，也不信任它的可用性。多提供商抽象（重试上提 + 三级结构化输出解析）→ Tool-use Agent（13 工具双协议 + 服务端会话）→ SymPy 确定性验证闸门（三态聚合）→ 确定性优先的 Word 导入拆题。

**仓库证据**

**面试怎么讲（含可能的追问与答法）**

核心叙事：「我把重试从各 SDK 上提并禁用 SDK 内建重试避免双重重试；结构化输出不赌 JSON mode 而用三级提取兜底；任何提供商缺依赖缺 Key 都静默降级 mock，克隆即可跑通全链路。输出侧再加一道 SymPy 确定性验算闸门——无法判定记 uncertain 而不是冤枉成 failed。这个闸门上线以来曾静默失效数日（09-27 引入、09-30 修复，git log 可查），靠全覆盖测试挖出三处 bug，这个教训让我重新审视 broad except 的代价。」

- **问：「为什么不直接信 JSON mode？」** 答：三级提取兜底 + 8 个边界测试（含拒绝 Python dict repr 的用例），把解析从概率问题变成确定性问题。

- **问：「批量导入为什么先做规则识别？」** 答：题号结构识别成功就零成本零超时直接拆，识别不出才分段走 LLM 且单段失败不烧掉整批——这是从一次真实导入超时故障修出来的策略（commit 263a3f7），有专门测试保证结构路径完全不触 AI。

**诚实短板**

- 提供商选择是启动期一次性决策，无运行时故障自动切换（provider A 挂了不会切 B）；重试无指数退避/抖动；遥测单机无跨实例聚合。
- Agent 无并行工具调用与流式中途取消；`self.history` 无窗口裁剪（长会话 token 无上界；服务端重建历史 `history_for_agent` 默认截 20 条，仅此一处有界）；eval_tutor 裁判是同一模型自评非独立评测。
- 验证结构仅「代回求解/导数互逆」两类；数值兜底仅 5 个采样点且限单变量；`answer_verifier.py:31` 的 `except Exception` 至今仍会吞验证器异常（正是当年静默失效的机制）未加告警计数；线上拦截幻觉无统计。
- 导入门禁阈值为启发式，未在多来源真实文档集验证泛化；AI 拆题路径质量无量化评测。

### 2.5 安全与认证（deep）

**能力说明**

两条主线：其一，「失败也不泄露」的贯穿决策链——教师邀请码 fail-closed、IDOR 统一 404 防存在性枚举、错误信封细节只进日志，并用泄漏断言测试锁死；其二，JWT 双令牌生命周期 + token_version 集中吊销，解决无状态 JWT 天然不可吊销的问题。

**仓库证据**

- 教师邀请码未配置即关闭教师注册（fail-closed），注释明示「教师身份会放大为全量学生数据可见」（`backend/services/auth.py:47-57`）；`tests/test_sprint_a.py:24-95` 服务+API 双层四分支（禁用/错码/对码/学生免验）。

- 错误信封：全局 500 返回统一 detail=服务器内部错误 的 JSON 信封（`api/main.py:83-86`）；AI 失败转 502 固定文案、原始异常仅进日志（`api/routers/questions.py:121-132`）；SSE 响应头已发出只能以 error 事件+[DONE] 兜底（`api/routers/agent.py:45-48`，取舍写在 `tests/test_error_envelope.py:112` 注释）；专项套件 7 例断言上游 URL/密钥/Traceback 绝不出现在响应且细节只落日志（`tests/test_error_envelope.py:56-187`，材料子集实跑 29 passed 内执行）。CHANGELOG v2.11.0（`CHANGELOG.md:25`）原文：**「错误信封：SSE 不再外泄原始异常（固定文案+日志）、502 消息脱敏、全局 500 处理器」**。
- JWT：access 30min/refresh 7d + typ 声明，旧令牌无 typ 按 access 平滑兼容（`backend/utils/tokens.py:25-62`）；claims tv ≠ user.token_version → 401 集中吊销（`api/deps.py:96-98`）；refresh 轮换时复验 tv 并出新令牌对（`api/routers/auth.py:76-89`）；登出/改密均递增 token_version（`auth.py:92-98`、`services/auth.py:73`）；`tests/test_token_revocation.py` 五例 + `tests/test_security.py:75-91` 令牌类型混淆均在材料实跑子集内执行。

**面试怎么讲（含可能的追问与答法）**

核心叙事：「我把『错误信息即攻击面』做成了可回归测试的契约——测试模拟内部异常，断言内部主机名和密钥不出现在任何客户端响应里。认证侧用『无状态 JWT + 用户级 token_version 单字段』混合方案解决 JWT 天然不可吊销的问题。」

可能的追问与答法：

- **问：「为什么权限不足也返回 404 而不是 403？」** 答：403 会泄露资源存在性，统一 404 防存在性枚举（`comment_service.py:14-19`），并有跨用户读/写/删三向测试钉住。
- **问：「JWT 无状态，怎么吊销？」** 答：用户级 token_version 单字段——改密/登出一次性递增吊销全部旧令牌，校验集中在 deps 一处；并为存量无 typ/tv 的旧令牌预留平滑升级约定（旧令牌按 access 处理）。
- **问：「SSE 里出错怎么办？响应头已经发出去了。」** 答：无法再换状态码，只能以 error 事件+[DONE] 兜底——这个取舍明确写在测试注释里（`test_error_envelope.py:112`），不是口头承诺。

**诚实短板**

- 无类型化领域异常体系，状态码转换靠路由层宽 except Exception；`error_messages.py` 单点文案仅 1 条常量；信封一致性靠约定+测试而非框架层强制。
- `comment_service` 仍保留 viewer_id=None 跳过归属校验的旧路径（代码内自认遗留债务）。
- 邀请码为明文常量比对，无哈希/过期/轮换机制。
- 吊销粒度是用户级全吊销，无单设备/单令牌维度；refresh rotation 无 reuse-detection（登出前旧 refresh 在 tv 未变窗口内仍可换新一次）。

2. **补齐 reaper 与 Redis 限流 except 回退分支的测试（small/high）**：降级设计块的叙事是「每条降级路径有测试守护」，但 reaper（2026-10-01 复核 `findstr /s /n "reap" tests\*.py` 零命中）与 `deps.py:46-51` 的 Redis except 回退分支恰是反例——需精确：后端**选择**路径已由 `tests/test_redis_request_limiter.py:35-71` TestBackendSwitch 覆盖，缺的是**异常回退分支**用例；各补 1-2 个用例即可让该块证据完全自洽。

## 四、面试使用建议

**讲述顺序（先立可信度，再秀深度，最后亮短板）：**

1. **开场 60 秒用可机械验证的事实立信**：先报实测数字（358 用例、147 提交、79% 覆盖率、ruff 全绿且为 CI 门禁——均以当场运行为准），并说明这些数字全部可以现场复现（见附录命令）。不要从「功能列表」讲起——面试官对功能不敏感，对「数字能复现、结论能对代码」敏感。
2. **第二个讲混合检索（2.3 节）**：这是「最能讲的一个函数」——从 `question_mixins.py:418-563` 逐段讲失败路径设计，再抛出 RRF 负收益的评测结论（33% vs 44%）。这一段同时展示工程能力（降级设计）、科学态度（评测驱动选型）和诚实（承认负收益）。
3. **第三个讲 AI 链路的验证闸门与静默失效教训（2.4 节）**：三态聚合的设计 + 「上线以来静默失效数日」的故事（时长说准：09-27 引入、09-30 修复，约 3 天，git log 可查——**不要夸大为「三个月」，一查即穿**）。主动讲失败经历比等面试官挖出更有说服力，且能自然引出 broad except 的反思。
4. **架构（2.1）与安全（2.5）按面试官背景取舍**：后端岗深讲分层验证与配置链（注意：分层叙事用修正后的准确版——零仓储依赖、无 HTTP 客户端，同时主动交代前端 3 处越层 import）；安全意识强的面试官深讲防泄露决策链与 token_version。
5. **降级设计（2.2）与质量工程（2.6）作为收尾**：前者给出「默认零依赖、坏了降级」的系统性总结，后者用诚实数字收束全场。

**怎么带面试官看代码（按此顺序开文件）：**

- `frontend/nav.py:23-33` → `question_service.py:6-7`：页面注册表与 session 取舍——决策是写进代码的，不是口头架构。
- `question_mixins.py:418-563` → `fusion.py:14-52`：检索管线全貌与失败出口。
- `answer_verifier.py:21-73` + CHANGELOG v2.11 + `git log -- backend/services/math_verifier`：验证闸门设计与教训（含可查证的时间线）。
- `tests/test_error_envelope.py:56-187`：泄漏断言测试——「错误信息即攻击面」的可回归契约。
- `.github/workflows/ci.yml`：lint 门禁 + 四层测试如何落进 CI，以及（诚实指出）覆盖率门禁还缺什么。

**主动亮短板的策略：**

- 每个能力块的「诚实短板」先于面试官说出，尤其三处已量化事实：覆盖率 79% vs 文档 ~90% 且无门禁、数字漂移链（287→335→340→353→358 / 144→147 / 11-12 版迁移）、reaper 与 Redis except 回退分支零测试——然后立刻接提升路线对应条目，把短板转述为「我知道怎么修、按什么顺序修」。
- 分层叙事务必用修正后的准确边界（前端零 repositories 依赖、无 HTTP 客户端；3 处越层 import 如实列出），不要沿用「前端只 import services」的过强表述。
- 被问到材料中未实现的需求（如「分段容错」仅到单次 AI 调用重试粒度、未评估 FSRS）时，直接承认未实现并说明当前边界，不包装。
